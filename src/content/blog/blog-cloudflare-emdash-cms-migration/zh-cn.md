8 月 12 日，Cloudflare 完成了一件看似平常的事：把官方博客从第三方 CMS 迁移到了自研的 EmDash。新博客上线了深色模式，视觉更现代化。

但这次迁移背后，藏着很多独立博主和开发者值得关注的细节。Cloudflare 团队在官方博客里详细复盘了整个过程，包括作为"零号客户"踩过的坑。

## 什么是 EmDash？

EmDash 是一个专为 Astro 框架和 Cloudflare 环境打造的内容管理系统（CMS）。它的设计目标是：让内容团队能够在熟悉的编辑界面里工作，同时享受 Astro 的性能优势和 Cloudflare 的全球边缘网络。

简单说，就是**把"写文章"和"部署博客"这两件事无缝连接起来**。

Cloudflare 为什么不做？他们已经有了：
- **Astro**：静态站点生成框架，性能优异
- **Cloudflare Pages**：全球 CDN 托管，免费额度慷慨
- **Workers**：边缘计算能力

EmDash 填补的是"内容编辑体验"这一环。

## "零号客户"：自己先当小白鼠

Cloudflare 有个很特别的内部文化：**Customer Zero（零号客户）**。什么意思？就是自家的产品，自己先用。在付费客户碰到问题之前，Cloudflare 会在自己的大规模基础设施上先验证一遍。

这个理念甚至被写进了内部工程标准 Codex 里。

所以，当 EmDash 发布后，Cloudflare 博客团队就成了它的第一个真实用户。他们带着两个核心问题开始迁移：

1. **EmDash 能不能满足我们的需求？**（好不好用）
2. **EmDash 能不能扛住我们的规模？**（稳不稳定）

第一个问题通过大量用户流程测试来验证：发布文章、定时发布、取消发布、添加媒体素材、编辑署名信息……整体表现不错。

但第二个问题，暴露了 EmDash 的多处短板。

## 暴露的问题：规模是把放大镜

Cloudflare 博客的体量很大：
- **媒体文件多**：历史文章累积了大量图片、视频
- **内容实体搜索复杂**：需要快速检索数千篇文章
- **署名信息丰富**：多位作者、guest post、协作编辑

在这些场景下，EmDash 的性能问题被放大了：

**1. 本地化支持不完善**
EmDash 在处理多语言内容时，没有完全满足 Cloudflare 博客的全球化需求。某些语言版本的文章在发布后，元数据丢失或格式错乱。

**2. SEO 细节处理粗糙**
作为企业博客，SEO 是核心指标。但 EmDash 在生成 sitemap、处理 canonical 标签、管理 meta 信息时，不够精细。团队不得不手动调整很多细节。

**3. 内容安全策略（CSP）适配不足**
Cloudflare 对安全要求极高，EmDash 在某些场景下触发了 CSP 警告，需要额外的配置和调试。

这些问题在小型博客上可能不明显，但在 Cloudflare 这样的规模下，每一个小瑕疵都会被放大。

## 为什么 Cloudflare 还是选择迁移？

既然有这些问题，为什么 Cloudflare 还要迁移？

答案在他们的文化里：**如果你想用外部供应商的产品，得先证明自家产品为什么不行。**

这次迁移本身就是对 EmDash 的压力测试。Cloudflare 博客团队在迁移过程中记录了每一个问题，反馈给 EmDash 开发团队。这些真实场景的 bug 报告，比任何测试用例都更有价值。

而且，从长期来看：
- **成本可控**：不再依赖第三方 CMS 的订阅费用
- **定制自由**：可以根据 Cloudflare 的特殊需求修改 EmDash 源码
- **技术栈统一**：Astro + Cloudflare Pages + EmDash，全链路在自己掌控中

## 对独立博主的启示

看到这儿，你可能会问：**这跟我有什么关系？我又不是 Cloudflare。**

其实关系很大。EmDash 是开源的，你完全可以用它来搭建自己的博客系统。Cloudflare 的踩坑经验，对你也是宝贵的参考：

**1. 规模决定选型**
如果你的博客只有几十篇文章，EmDash 可能绰绰有余。但如果有上千篇内容、大量媒体文件、多作者协作，就要考虑它的性能瓶颈。

**2. 迁移前要做全面测试**
Cloudflare 作为"零号客户"，迁移后暴露了问题。你如果迁移到 EmDash，也要先在测试环境里跑一遍核心流程：发布文章、上传图片、设置 SEO 信息、检查移动端适配。

**3. 自建 CMS 的隐形成本**
Cloudflare 有工程师团队维护 EmDash，你作为独立博主，要评估自己是否有能力处理突发的 bug 和安全更新。有时候，付费的第三方 CMS（如 Ghost、Contentful）反而更省心。

**4. Astro + Cloudflare Pages 依然是黄金组合**
无论用什么 CMS，底层的 Astro 和 Cloudflare Pages 都是非常成熟的技术选型。EmDash 只是补齐了"内容编辑"这一环，你完全可以用 Astro + Cloudflare Pages + 任何你喜欢的 CMS（甚至直接用 Markdown 文件）。

## 我怎么选？

如果你问我，作为一个独立博主，要不要迁移到 EmDash？

我的建议是：

**如果你的博客已经稳定运行，且没有强烈的"后台编辑"需求，** 先不要动。EmDash 还在快速迭代，Cloudflare 博客团队发现的问题会在后续版本中修复。等它更成熟了再考虑。

**如果你正在搭建新博客，且希望有一个现代化的后台编辑体验，** 可以试试 EmDash。它是开源的，部署在 Cloudflare 上也很方便，就算后来不满意，迁移成本也不高。

**如果你对性能和稳定性要求极高，** 还是老老实实用 Astro + Markdown 文件 + Git 的方案。这虽然"原始"，但也是最可控、最不易出问题的方式。

Cloudflare 的这次迁移，本质上是把"产品验证"和"用户使用"合二为一。他们既是开发者，也是用户。这种模式对大公司来说可行，但对个人博主来说，风险可能大于收益。

技术的选择，从来不是追求"最新"，而是找到"最适合当下需求"的那个平衡点。EmDash 很有意思，但它适不适合你，得你自己判断。
