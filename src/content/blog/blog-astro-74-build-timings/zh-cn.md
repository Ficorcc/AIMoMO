## 构建慢，但不知道慢在哪

做静态站的人都有过这种体验：项目越来越大，构建时间越来越长，但你根本说不清到底是哪里出了问题。是某个 Vite 插件拖慢了速度？还是某篇长文章的 Markdown 处理太耗时？或者是渲染某个特别重的页面？

以前你只能靠猜——加个日志、减个插件、换个配置，然后重新跑一遍看有没有改善。效率很低，而且经常治标不治本。

现在 Astro 7.4 给了一个更直接的答案：`--timings` flag。

## 这个新功能到底能做什么？

当你运行 `astro build --timings` 时，Astro 会在构建完成后打印一份详细的时间分布报告：哪些阶段花了多少时间、Vite 插件贡献了多少、Markdown 处理和语法高亮占了多少、页面渲染和图像处理各用了多久、各个集成又消耗了多少资源。

这听起来是个小功能，但对实际开发来说意义重大。因为它把原本模糊的"构建很慢"变成了具体的数据：你可以一眼看出是哪个环节在拖后腿，然后有针对性地优化。

比如你可能发现，原来问题不在框架本身，而是某个第三方插件在处理图片时卡住了；或者发现某篇文章的评论组件每次都在拉取外部 API，导致渲染变慢。有了这些数据，优化就有了方向。

## 其他值得关注的改动

除了 build timings，7.4 还有几个同样实用的改进：

- **不同 image services**：你可以为预渲染页面和按需加载的页面分别配置不同的图片服务。这意味着你可以在不影响首屏性能的前提下，灵活选择图片处理方式。
- **notFound() handler**：自定义入口点的 404 处理器，让错误页面的定制更加自由。
- **font configuration warnings**：字体配置警告，帮你提前发现那些 CDN 可能无法提供的字体设置。
- **并行预渲染（实验性）**：跨 worker 线程并行预渲染，理论上可以进一步缩短大型项目的构建时间。
- **自定义重定向页（实验性）**：为静态构建提供自定义的重定向页面支持。

这些改动里最让我感兴趣的是并行预渲染。虽然还是实验性功能，但它指向了一个明确的方向：当项目规模变大时，Astro 需要更多的并发能力来保持构建速度。

## 为什么这对独立开发者很重要？

对于用 Astro 建站的人来说，构建速度直接影响的是开发体验和部署效率。尤其是那些内容驱动的网站——博客、文档站、营销落地页——它们往往有大量页面需要生成，构建时间的每一秒都意味着等待成本的增加。

更重要的是，7.4 的这些功能让"性能优化"这件事变得可操作了。过去你可能觉得自己的站点已经够快了，但现在你能看到具体哪个环节还能提升，从而做出更有针对性的调整。

## 我的判断

我觉得 Astro 7.4 最值得肯定的地方不是它加了什么花哨的功能，而是它开始正视"构建慢"这个问题，并给了开发者一套工具来诊断和优化。

当然，实验性功能的稳定性还需要观察。如果你打算在生产环境使用并行预渲染或自定义重定向页，建议先在小范围测试一下。但对于大多数用户来说，build timings 已经足够实用了——毕竟，知道自己为什么慢，比盲目加速重要得多。

升级也很简单，运行 `npx @astrojs/upgrade` 就能自动完成。如果你的项目还在用旧版本，不妨趁这次机会看看构建报告，说不定能找到一直困扰你的性能瓶颈。
