如果你的站点挂在 Cloudflare 后面，你可能遇到过这种玄学：明明开了缓存，命中率却低得可怜，源站该扛的流量一点没少。很多时候，罪魁祸首是一个叫 Vary 的响应头。

10 月 25 日消息，Cloudflare 终于动手了：在全球边缘网络原生支持 HTTP Vary 响应头，并通过 CacheRules 向所有套餐开放。用官方自己的话说，这是治理「缓存抖动」的标准化方案。

先解释一下问题出在哪。按 HTTP 标准语义，Vary 头用来告诉下游缓存：源站在生成这个响应时，检查了哪些请求头。比如一个多语言站返回 `Vary: Accept-Language`，意思是「中文用户和英文用户看到的内容不一样，你别混着缓存」。

听起来很合理，但 CDN 一直对 Vary 头很谨慎。因为客户端请求头的写法五花八门：空格、大小写、语言优先级顺序，稍微不一样，同一个资源就可能被拆成几十个缓存变体。缓存碎片化了，命中率暴跌，源站负载飙升。

Cloudflare 这次做了一项实证审计：覆盖约 5 万个热门域名、超过 1.2 亿条 HTTP 响应，结果发现近 3000 个源站会根据四个或更多请求头生成不同响应，极端情况下涉及数十个字段。也就是说，缓存抖动不是理论风险，是普遍存在的现实问题。

怎么治？Cloudflare 的方案是两阶段架构：源站继续指定哪些请求头会影响响应生成，但边缘节点怎么处理这些请求头的值，由 CacheRules 说了算。具体有三种操作：规范化，把 Accept、Accept-Language 这类复杂的协商头转换成标准化等价类，消除客户端之间的无意义差异；原样传递，存储精确且区分大小写的字符串，适合源站依赖精确 Token 匹配的场景；绕过缓存，对匹配易变请求头的请求直接跳过边缘缓存，避免不确定的响应变体占用缓存容量。

翻译成人话就是：以前 Vary 是「源站说了算、CDN 只能硬着头皮执行」，现在 CDN 有了自己的判断权——知道哪些差异无关紧要可以归一化，哪些必须精确保留，哪些干脆别缓存。

对独立博客站长来说，这算是个好消息。尤其是这几类站点：做了多语言版本的博客，响应式图片按 Accept 头给不同格式，或者 API 按客户端类型返回不同内容的站。以前要折腾禁用缓存、写 Cloudflare Workers、维护自定义缓存键这些歪路子，现在在 CacheRules 里配几条规则就行，免费套餐也能用。

从更大的视角看，Cloudflare 这一手其实是在重新定义「缓存的信任边界」。传统 CDN 的思路是「源站说的都对，我照做」；新思路是「源站声明依赖，我来决定怎么处理依赖」。这是把缓存从被动执行变成主动治理，我觉得会是整个行业的方向。

当然，也不是没有坑。Vary 处理规则配错了，可能出现两种后果：该区分的内容被合并缓存，用户看到错误版本；或者该缓存的被绕过，性能反而下降。所以上线前最好先在测试域名上观察缓存命中率的变化，别一上来就全站铺开。

我的总结：Cloudflare 原生支持 Vary，是把一个困扰站长多年的缓存难题从「民间偏方」变成了「官方标准配置」。对大多数独立博客来说，这意味着更省心的缓存、更低的源站压力，也意味着我们终于可以少花时间跟缓存玄学搏斗，多花时间写内容了。
