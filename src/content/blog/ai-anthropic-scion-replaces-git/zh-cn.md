Git 大概是开发者默认世界里最「不需要解释」的工具之一。你写代码、提交、推送、合入，全世界都这么干。但 Anthropic 最近做的事，相当于说了一句狠话：这个默认，在我家不够用了。

数字摆出来确实吓人。Anthropic 内部日均合并的代码变更，从 5 月的约 2500 次，涨到 9 月的超 3 万次；单体仓库每天要处理约 2500 万次检出。如果继续走传统 Git 的路线，光这块流量就超过 600PB。这已经不是「仓库有点大」的问题，是基础设施被写代码的速度撑爆了。

于是他们没等开源社区给方案，直接自己造了一个：Scion。7 人团队，5 个月，把一个版本控制系统的核心思路整个翻了过来——计算放在服务端，客户端按需取数，各层缓存命中率做到超 99%，检出从几分钟缩到几秒。配合 Claude Mythos 预览版重写迁移管道，内存降到原来的二十分之一、提速 4 倍。

我觉得真正有意思的，不是 Scion 这个工具本身，而是它暴露了一个正在发生的结构性变化：**代码的生产速度，已经从「人肉」切换到「机器」了。**

Git 的设计前提，是人在本地工作、仓库是主干、变更由人审阅合并。这个前提在「AI 每天产出成千上万行代码」的场景下，处处都是摩擦点。3 万次日均合并意味着什么？意味着按人类节奏做 code review 根本来不及，传统 Git 的检出、拉取、diff 计算，全在给「AI 流水线」当瓶颈。Scion 的解题思路——服务端计算、客户端按需、缓存命中——本质上就是在说：别再让每个客户端都拖一遍全量历史了，算力集中、取用分离，这才是 AI 原生开发规模的答案。

另一个值得品味的细节：Anthropic 目前无意开源 Scion，并且判断其他团队 6 到 12 个月内也会撞上同一堵墙。这句话的潜台词是，他们不认为这是 Anthropic 一家的特例，而是整个 AI 重度开发团队迟早要面对的问题。等撞墙的人多了，Git 不再自动成为默认答案，「版本控制」这个概念本身会被重构——服务端优先、按需取数、缓存命中率，这些词会变成下一代开发者工具的标准卖点。

当然，对大多数普通开发者来说，Git 短期内不会消失，日常项目也没必要换。但这件事值得看见：当代码量以 AI 的速度膨胀时，最先崩溃的不是编辑器，不是模型，而是协作层。Anthropic 用 5 个月证明了，这个瓶颈可以被正面解决，也顺便预告了未来工具链的形态。

我的判断是，Scion 最大的价值未必是替代 Git，而是把一个问题摆到了台面上：我们习以为常的开发者基础设施，是按「人类写代码」的规模设计的。一旦写代码的主力变成 AI，从头重想一遍工具链，就不再是极客行为，而是刚需。下一个「Git」，可能不是某个改进版的 Git，而是一套为机器协作速度设计的全新协议。
