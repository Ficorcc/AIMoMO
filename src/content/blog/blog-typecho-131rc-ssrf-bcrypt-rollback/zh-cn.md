用 Typecho 的人最近该看一眼后台了。1.3.1-rc 出来了，官方明说"没有新功能，主要是一组安全修复"，紧跟着一句更重要的：这次改动里，有两项在你换回 1.3.0 之后不会被撤销。

我把发布说明和 CVE 记录都过了一遍，下面按"洞是怎么回事、修了什么、哪些回不去"讲。

## 洞在 Pingback，一个没人用但一直开着的功能

CVE-2026-7025，影响 Typecho 1.3.0 及更早的全部版本，CVSS 6.9，中等。攻击可以远程发起，PoC 已经公开。

问题出在 `var/Widget/Service.php` 的 `Service::sendPingHandle`。Pingback 是博客之间互相引用时用来通知对方的机制，入口挂在 `/action/service`，请求里带上 `do=ping` 就走到发送逻辑。正常来说这里要先校验一个 token，token 是拿密钥和时间戳算出的 sha1 字符串。问题在于校验那一行用了 PHP 的松散比较 `==`——只要把 token 传成布尔值 `true`，不管 sha1 算出什么，跟 `true` 一比都成立。不用登录，不用任何凭证。

过了校验之后更麻烦。发送逻辑会拿攻击者给的地址去发请求：第一跳访问那个地址，从返回内容里读 `X-Pingback` 头、或者读页面里声明的 pingback 链接；第二跳再拿这个地址发 XML-RPC 请求。两跳都没有做目标地址校验，而且第二跳的地址完全由攻击者控制——因为第一跳的响应本来就来自攻击者自己的服务器。

结果就是，可以让你的服务器去访问 `127.0.0.1`，访问 `10.x` 段内网，访问云主机上那个 `169.254.169.254` 元数据地址。这些地址从公网本来碰不到，但从你的服务器上出发就不一样了。

这个洞在 10 月中旬就被公开分析和贴过临时补丁，当时官方最新版还是 1.3.0，框架里判断内网地址的 `checkSafeHost()` 早就写好了，只是 pingback 这条路径上从来没人调用它。1.3.1-rc 就是官方把这条路补上的版本。

## 修法比补一行判断更彻底

官方这次的 SSRF 修复思路，我觉得值得单独说一下：没有只加一层地址过滤，而是把所有出站请求统一收敛起来——解析目标地址、只允许公网地址、然后把校验过的 IP 固定住（pin）用于这次连接。

最后这个"pin IP"是关键。如果只校验域名解析结果、然后重新发一次请求，攻击者可以做 DNS rebinding：第一次解析成公网地址过校验，第二次解析到内网地址。把校验过的 IP 钉死再连，这个手法就失效了。

同一批还修了另外几处：`timeToken` 现在会拒绝非字符串输入（布尔、数组、数字一概挡掉）并改用 `hash_equals()` 做恒定时间比较，顺带把 `asyncHandle()` 一起修了；页面模板名字以前是原样写入，现在只接受当前主题实际提供的模板；低于编辑者权限的用户以前能触发不该有的状态变更，现在按角色拦住；评论管理页遇到非法 UTF-8 会返回空字符串，现在会替换掉异常字节；Trackback 摘要以前原样入库，能把标记带进后台，现在按 pingback 的方式清洗。

还有一项大工程：整个 XML-RPC 层被重写了。这层是 MWeb、Open Live Writer 这类客户端远程写作的入口，多年没人维护，攒下了一堆日常使用就会踩到的问题。

## 回不去的两件事

现在说到重点。

**第一，密码哈希迁移不可逆。** 1.3.1 把哈希从 phpass（256 轮 MD5）换成 `password_hash()` 生成的 bcrypt，已有账号在登录时自动迁移。麻烦在于方向只有一条：某个账号一旦在 1.3.1 上登录过或改过密码，库里存的就是 bcrypt；这时候你把程序文件换回 1.3.0，这个账号——包括管理员——直接登录不了，因为 1.3.0 只认旧格式。

官方给的补救办法是一句 SQL：

```sql
UPDATE typecho_users SET password = MD5('temporary-password') WHERE uid = 1;
```

也就是说，先把密码改回旧格式的临时值，才能回去。这也解释了为什么官方反复强调"先在副本或本地环境试"——要备份的不是文件，是数据库。

**第二，XML-RPC 的行为变了，而且是静默的那种。** `metaWeblog.editPost` 现在遵守 `publish` 参数的默认值：不带这个参数，文章会直接发布，不再默认存草稿。用 MWeb 或 Open Live Writer 的人，以前写一半发出一个不带 publish 的请求，得到的是草稿；现在得到的是线上文章。这不是 bug，是修复，但它会在你毫不知情的时候改变结果。

顺带几个同类改动：空字符串参数以前会被丢弃，导致后面每个参数错位一位；字符串以前会被 trim，Markdown 代码块里的缩进就这么没了——这两条都修好了，但如果你有客户端依赖旧的错位行为，得重新测一遍。

还有一个副作用值得提醒：出站请求现在会 pin IP。如果你的服务器走代理出网、或者 DNS 解析方式比较特殊，升级后要回头验证一下 pingback 发送和附件抓取还能不能正常工作。

## 我的判断

我想说的是这份发布说明本身。它把"回不去的地方"单独拎出来做成一个 Before you upgrade 章节，而且写得足够具体——具体到给了回滚用的 SQL，具体到指出哪个函数调用不受影响（插件里调 `PasswordHash::hashPassword()` 的不受影响，那个类行为没变）。

这个写法在我看过的开源项目里不算常见。11 月 9 日我写过 WordPress 那个 CVE-2026-119977，那次的问题是"更新这个动作本身被利用"；这次 Typecho 的问题是另一层——升级的退路被切断了。两个风险不在一个层面上，但都指向同一件事：升级不该被默认当成安全操作。

给还在 1.3.0 的人两条路。不着急的，等 1.3.1 正式版；站点暴露在公网又急着堵洞的，可以先走网络层，把 `/action/service` 封掉——nginx 里那条正则要写在 `location ~ \.php` 之前（正则 location 之间取最先匹配，顺序错了等于没写），而且要同时覆盖 `/action/service` 和 `/index.php/action/service` 两种形式，攻击用的恰恰是带 `index.php` 的那种。代价是站内正常 pingback 和依赖 `do=async` 的异步调用会一起失效，现代博客基本不用这些，能接受。

要上 RC 的，就别图省事。我自己的做法永远是：先复制一份站点到本地容器，跑一遍完整登录、发文章、传附件、发一条 pingback，再动线上。备份数据库这件事，在这套流程里是最便宜的一步，也是最不该省的一步。
