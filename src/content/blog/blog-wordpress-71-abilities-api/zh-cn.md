WordPress 7.1 正式版在8月19日悄然上线了。相比7.0发布时"原生集成AI"的热闹宣传，7.1显得低调很多。但我在看更新日志时发现了一个有意思的细节——**Abilities API 引入了 meta.public 元数据标志**。这个功能看起来不起眼，但它真正解决了一个实际问题：让你的 WordPress 网站，变成 AI Agent 的"可编程接口"。

## Abilities API 是什么

简单说一下背景。WordPress 7.0 带来了 Abilities API——一种标准化的方式，让外部系统（比如 AI 助手）知道 WordPress 网站"能做什么"。你可以理解为它给每个网站功能都贴了一张标签："这里可以发文章""这里可以读取评论""这里可以管理媒体库"。

问题是：这些能力是全开放还是半开放？外部 AI 是否应该被允许访问某个能力？

## meta.public 的意义：给AI划定边界

这才是 7.1 的关键变化。

Meta.public 标志的作用，是让开发者**精确控制**某项能力是否对外部 AI 开放。比如：

- `wp:posts:create` — 发布文章的能力，默认可能是关闭的（你不想让任何 AI 随意在你的博客上发文章）
- `wp:posts:read` — 读取文章的能力，可以设为公开（AI 可以阅读你的内容）
- `wp:admin:access` — 管理后台的能力，显然不应该是 public

这个设计背后的逻辑很清晰：**AI Agent 能做什么，由博主说了算。** 不是一刀切全开放，也不是全锁死，而是让每个能力独立可控。

## 对独立博主意味着什么

如果你是 WordPress 用户，这个变化可能暂时还感受不到——因为它主要面向开发者。但它的影响会在接下来的几个月里逐渐显现：

**AI 写作工具会更容易"接管"你的博客。** 当 AI Agent 能以标准化的方式，知道"我可以在这个博客发文章、读取评论、上传图片"，建站工具和 AI 助手之间的对接成本会大幅降低。未来你可能会在 AI 写作工具里直接选择"发布到我的 WordPress 博客"，而不需要手动复制粘贴。

**博客的数据边界会更清晰。** 有了 meta.public 的声明机制，AI 能访问什么、不能访问什么，博主可以逐项配置。这比现在的"要么全部，要么没有"要安全得多。

## 但我更想聊聊它对博客生态的长远影响

我在之前的文章里聊过 WordPress 7.0 内置的 MCP 适配器——它让 Claude Code 可以直接读写 WordPress 博客。这次 7.1 的 meta.public ，相当于把这个能力进一步精细化了。

我有一个判断：**独立博客的下一阶段演进，不只是"用 Astro 做静态站"或"用 WordPress 做动态站"，而是博客本身会成为 AI Agent 工作流里的一个节点。**

你的博客不只是给人看的，它也是给 AI Agent 看的——AI Agent 会帮你管理内容、分发内容、分析内容。WordPress 正在把自己定位成这个图景里的"内容基础设施"。

这是好事还是坏事？我没有确定的答案。但有一点是肯定的：**技术门槛在降低，创作门槛在降低，下一步的竞争，将是"谁的内容真正有价值"的竞争。** 工具越来越智能，只会让真正有独立思考的博客，变得更稀缺。
