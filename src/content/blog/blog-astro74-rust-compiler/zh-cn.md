Astro 最近几个版本很有意思——它没有忙着加花哨功能，而是把力气花在了"快"和"看得懂"上。10 月 19 日发布的 7.4.1 稳定版，加上 7.0 以来的底子，讲了一个非常朴素但值钱的故事：把最慢的两段代码换成 Rust，再给你一份能读懂的性能报告。

先看它干了什么。Astro 7.0（今年 6 月发布）把组件编译器从 Go 版整个换成了 Rust 版，Markdown 与 MDX 的处理也换成了自研的 Rust 管线，渲染引擎改成基于队列的策略。为什么动这两块？因为静态站构建分三步，最费时间的就是"把页面、内容、组件打成包，再逐个预渲染成 HTML"，而其中编译与 Markdown 处理又是最慢的两段——这正好是几千篇 Markdown 攒出来的内容站最痛的地方。

另一半提速来自 Vite 8。这一版 Vite 最大的变化是内置了一个用 Rust 写的打包器，把原来分工的两个工具并成一个，插件接口还保留着。合并之后，官方给的区间是整体构建时间快 15% 到 61%，个别站点能快到两倍以上。基准数字更直观：一个六千多页的文档站，构建从 114.54 秒降到 73.53 秒；一万三千页的大站从 385.84 秒降到 326.11 秒。

注意，页数越多的站，百分比上的收益反而越小——因为页面渲染本身没被搬进 Rust，页数多了它占的比重就上来了。换句话说，这次升级的收益大小，取决于你的站有多少时间花在编译和 Markdown 上。像 aimomo 这种几百篇中文 Markdown 的博客，正是典型受益户；而那种全站几十个页面、几乎不碰 Markdown 的营销页，可能感受就没那么明显。

如果说 7.0 解决的是"更快"，7.4 解决的是"快在哪、慢在哪"。构建命令多了一个 --timings 参数，跑完打印明细：各阶段、各插件、Markdown 处理、语法高亮、页面渲染、图片处理，每一项耗时和占比清清楚楚，还附带最慢页面的中位数与高位值。

官方用博客起始模板演示了一下，效果相当治愈：模板只有 9 个页面，总耗时 2.61 秒，其中页面生成占 2.10 秒、80.6%，最慢的全是套用文章布局的页面。原因也很典型：布局里先取评论、每条评论再取作者资料，两轮请求串在一起，每个页面都在干等。改成一次性并发取回后，页面生成从 2.10 秒降到 1.13 秒，每篇文章渲染时间减半。这个例子的价值不在那 1 秒，而在于——没有报告的时候，这段代码在编辑器里看起来毫无问题，你根本不知道该改哪。

有几个升级细节也值得提醒。换了 Rust 编译器之后，对不合法的 HTML 语法更严格了：未闭合的标签直接报错，非空元素必须有配套闭合标签，语义上不合法的嵌套不再被自动纠正。旧编译器会悄悄帮你补标签、调顺序，新编译器选择不帮。所以升级后跑一遍构建，看到以前没见过的报错别慌，把未闭合标签补齐、回头查一下模板嵌套就行。模板规整的项目几乎无感，历史包袱重的项目等于一次免费体检。

另外，7.4 还抬高了最低 Node.js 版本到 22.22.0，把 src/fetch.ts 设为保留文件名，图片服务可以拆成"构建期本地优化 + 运行时图片 CDN"两套，新增了并行预渲染和自定义重定向页两个实验开关。如果你正在用 Astro，这些都不是必须马上改的，但值得记一笔。

我的判断是，Astro 7 这一代的价值不在某个新组件或新功能，而在工程哲学：把慢的部分换成更快的语言实现，再把说不清的部分做成能读的报告。前者靠一次重写完成，后者靠一个参数就够。对独立博客作者来说，构建从两分钟压到一分钟，你可能觉得"也就那样"；但当你真的打开 --timings，第一次看清是哪个布局、哪段取数在拖后腿时，那种"原来如此"的感觉，才是这轮升级真正值钱的地方——构建变慢时先看报告，再决定改哪里。
